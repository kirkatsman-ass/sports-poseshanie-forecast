# Посещаемость матчей и продажи билетов

Начальный репозиторий по теме 29 дисциплины «Прогнозно-аналитические системы».
Текущий этап: постановка задачи, источники и организация репозитория.
Все комплектные данные синтетические. Они не описывают реальный клуб.
Модели, EDA и дашборд ещё не реализованы.

## Цель

За 7 суток до домашнего матча прогнозировать итоговое количество проданных
билетов за вычетом возвратов и фактическую посещаемость. Основной пользователь —
менеджер билетной программы. Единица прогноза — матч; продажи хранятся по дням.

## Запуск

Требуется Python 3.10 или новее. Внешних Python-зависимостей нет.
Из корня проекта:

```sh
python src/pipeline.py demo
python src/pipeline.py ingest
python -m unittest discover -s tests -v
```

В Windows при необходимости замените `python` на `py`, в macOS/Linux — на `python3`.
Первая команда создаёт 120 матчей, 3600 дневных строк продаж и 120 погодных
прогнозов. Последующий ingest сообщает unchanged и не добавляет дубликатов.
Данные: data/raw; SQLite: data/processed/sports.db.
Каждый вызов загрузки добавляет диагностические строки в load_log; предметные
данные при повторном запуске не меняются. Полный demo заново создаёт исходные
демоданные: для своих файлов используйте только ingest.

## Воспроизводимость и конфигурация

config/settings.json задаёт seed=29, период, вместимость, горизонт,
пути к данным и параметры HTTP. Код не зависит от pandas или scikit-learn.
Для дальнейшей разработки можно создать окружение `python -m venv .venv`.
Сведения о CSV, форматах полей и происхождении: docs/sources.md.

## Источники

1. matches.csv — синтетические расписание и итоги матчей.
2. ticket_sales.csv — синтетические агрегированные продажи и возвраты.
3. weather_forecasts.json — синтетические внешние погодные факторы в JSON.
4. Open-Meteo — выбранный открытый API для дальнейших реальных погодных снимков.

```sh
python src/pipeline.py fetch-weather
```

Последняя команда требует сети. Она сохраняет отдельный исходный JSON и не
подменяет им синтетический архив. Проверка реального API в комплектные
автономные тесты не входит. Исторический реанализ нельзя выдавать за прогноз,
известный за 7 суток до матча. Для будущей модели нужны снимки прогнозов с
временем получения не позднее точки прогнозирования.

## Архитектура

CSV матчей и продаж + JSON внешних факторов → проверка схем и ограничений →
SQLite (records, source_state, load_log). Следующий этап: очищенные таблицы,
витрина признаков на момент D−7, три модели, временная валидация, дашборд.
Идентификаторы источников и записей образуют составной первичный ключ.
Изменение уже загруженной записи под тем же ключом отклоняется: нужна новая
версия и отдельная политика обновления. Удаления из файла не удаляют историю.

## Git и GitHub

В архив включён локальный Git-репозиторий с одним начальным коммитом.
Удалённый репозиторий не создан. Сначала настройте своё имя и email в Git.
Создайте на GitHub пустой репозиторий sports-attendance-forecast без README.
Подставьте реальный URL в следующую команду (строка YOUR_LOGIN — шаблон):

```sh
git remote add origin [https://github.com/YOUR_LOGIN/sports-attendance-forecast.git
git push -u origin main](https://github.com/kirkatsman-ass/sports-poseshanie-forecast)
```

Если архиватор удалил каталог .git, сначала выполните `git init -b main`,
`git add .` и `git commit -m "Initial project setup"`.
Не создавайте фиктивную историю за прошлые даты: дальнейшие коммиты делаются
по мере фактической работы. Инструкция импорта:
https://docs.github.com/en/migrations/importing-source-code/using-the-command-line-to-import-source-code/adding-locally-hosted-code-to-github
